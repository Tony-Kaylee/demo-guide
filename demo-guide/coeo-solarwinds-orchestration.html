Product architecture brief · COEO

SolarWinds orchestration with Revii + New Rev.io

What Rev.io would need to commit to, what the target operating model looks like, and which capabilities Product must validate or build before representing this as meeting COEO’s alert-correlation and flood-control requirements.

Demand: 30K–50K alerts/monthBursts: hundreds/minuteOutcome: ≈2,500 tickets/monthAssessment: custom integration / major gap
01

Executive answer

The integration is feasible, but it is not simply another alert-to-ticket connector.

Revii should be the orchestration and policy layer—not the system of record.

SolarWinds remains the monitoring authority; New Rev.io remains the customer, asset, agreement and ticket system of record. Between them, Revii operates a durable, deterministic event pipeline that qualifies, suppresses, correlates and governs alert state before making controlled PSA writes.

Reuse

Proven product primitives

Existing RMM/security integrations demonstrate ingestion, mapping, ticket creation, asset association and—in N-able/NinjaOne patterns—bidirectional ticket status.

Net-new

Network event intelligence

Persistent event state, topology-aware correlation, precedence rules, recovery timers, flood control and exception handling are not evidenced as current native capabilities.

Product boundary

Do not bury this in prompts

Revii may explain decisions and assist operators, but deduplication, timers, idempotency, topology and ticket mutations must be deterministic, testable services.

Bottom line: commit only as a jointly scoped orchestration product build with an explicit scale qualification—not as a configuration of today’s generic alert-to-ticket pattern.

02

Target architecture: seven stages

A queue-backed, stateful pipeline separates burst absorption from ticket creation and gives every decision an auditable reason.

1

SolarWinds ingest

Signed webhook/event receiver where available; resilient poller otherwise. Normalize alert, clear, acknowledge and mute signals into a versioned event envelope.

2

Durable buffer

Queue or event bus absorbs burst traffic. Persist raw payload, tenant, source ID, received time and replay metadata; enforce backpressure and dead-letter handling.

3

Identity & topology

Resolve SolarWinds nodes, interfaces, tunnels, circuits and sites to stable New Rev.io customer/assets/services. Materialize NNI and parent/child relationships.

4

Qualification engine

Apply maintenance windows, management tier, severity, duration, flapping and allow/deny rules before any ticket decision.

5

Correlation engine

Maintain event episodes; deduplicate repeats; roll child symptoms into a probable parent; apply packet-loss → latency → node-down precedence and flood policies.

6

Ticket state machine

Create or update one canonical New Rev.io ticket. Keep first seen, last seen, count and current state in structured fields—not a note per occurrence.

7

Control & write-back

Recovery timers and status-aware closure; SolarWinds acknowledge/mute; human exception queue; shadow mode, audit, replay, dashboards and operational controls.

04

What Product must validate or build

The work divides into connector capability, an orchestration control plane, and New Rev.io platform enablement.

Validate first

SolarWinds contract and authority

  • Which SolarWinds products/versions: Orion Platform, NPM, NCM, SD-WAN modules or custom properties?
  • Push versus polling, ordering guarantees, stable alert/event IDs and clear/reset semantics.
  • API support and permissions for acknowledge, unacknowledge, mute/unmute and maintenance windows.
  • COEO’s exact topology source of truth, NNI model and site/circuit identifiers.
Build

Durable event episode store

  • Tenant-scoped idempotency key and source-event ledger.
  • Open episode keyed by resource + condition + policy scope.
  • First seen, last seen, count, current state, clear/reopen history and ticket link.
  • Atomic transition/outbox pattern so retry cannot create duplicate tickets.
Build

Topology & identity model

  • Typed graph for site, node, interface, tunnel, circuit, NNI and parent/child edges.
  • Stable external identifiers mapped to New Rev.io records.
  • Effective-dated relationships and reconciliation for moved/replaced assets.
  • Explainable blast-radius query: “why was this child suppressed?”
Build

Policy and correlation engine

  • Configurable qualification, severity, management-tier and duration rules.
  • Precedence and supersession rules; parent/root-cause roll-up.
  • Debounce, flap detection, recovery grace timers and status-aware recovery.
  • Maintenance suppression, mass-event thresholds and per-site/customer guardrails.
Validate / extend

Ticket API semantics

  • Idempotent create/upsert or client-supplied correlation key.
  • Patch structured fields without creating notes, activities or time entries.
  • Read current ticket status before recovery action; protect manually closed/held/escalated states.
  • Asset, agreement/service, queue, priority and customer mapping at required throughput.
Build

Operator control plane

  • Shadow mode showing proposed decisions without PSA/SolarWinds writes.
  • Human exception queue for unmapped, ambiguous and policy-conflict events.
  • Decision trace, configuration version, replay and override with RBAC.
  • Dashboards for suppression ratio, duplicate prevention, lag, DLQ and ticket yield.
Validate

Security and tenancy

  • Per-tenant secrets, least-privilege SolarWinds accounts and credential rotation.
  • Payload retention, PII assessment, encryption and regional requirements.
  • Signed inbound requests, outbound allowlisting, RBAC and immutable audit trail.
  • Cross-tenant isolation tests and support access controls.
Build / operationalize

Reliability & lifecycle

  • Backpressure, retries with jitter, DLQ, replay and poison-event quarantine.
  • Schema versioning and safe policy deployment/rollback.
  • Reconciliation jobs against SolarWinds and New Rev.io after outages.
  • Runbooks, SLOs, telemetry, ownership and support escalation.
05

Scale and acceptance gates

Average volume is modest; burst behavior, correctness and false correlation are the real risks.

≥ 500/min

Burst qualification

Sustain an agreed peak above COEO’s observed “hundreds/minute,” with no loss, bounded queue growth and demonstrated recovery after a downstream outage.

0 dupes

Idempotency

Repeated delivery, timeout-after-write, replay and worker restart produce one event transition and at most one canonical ticket.

100%

Decision traceability

Every event is ticketed, suppressed, correlated, deferred or excepted with policy version and reason.

2,500

Ticket yield

Replay representative 30K–50K monthly alerts and demonstrate approximately COEO’s expected ticket volume without tuning on the test answer.

Additional release criteria

  • Golden scenario suite for packet loss → latency → node down, NNI parent failure, child flood, flapping and maintenance overlap.
  • No note/time-entry amplification from repeated alerts; counters update in place.
  • Recovery respects ticket state and configured grace period; a human escalation is never silently undone.
  • Topology mapping accuracy and unmapped-rate thresholds agreed with COEO.
  • Shadow-mode comparison against COEO’s current operation over a representative period.
  • Forced SolarWinds/API outage, New Rev.io throttling, partial write and stale topology tests.
  • Operator can replay safely and prove that write-back does not cause an integration loop.

Product must agree numerical SLOs with COEO for ingest lag, ticket latency, recovery latency, availability and tolerated exception rate before contract language is finalized.

06

Phased recommendation

De-risk semantics and operator trust before enabling autonomous suppression and write-back.

Phase 0 · Discovery and replay harness

Lock SolarWinds products/APIs, event samples, topology, business rules and New Rev.io endpoints. Build a sanitized historical replay set and golden expected decisions. Exit only when identifiers and state transitions are unambiguous.

Phase 1 · Shadow mode

Ingest and normalize production events; map topology; run qualification/correlation without creating tickets or muting SolarWinds. Give operators a decision log and exception queue. Measure projected ticket yield and false suppression.

Phase 2 · Controlled ticketing

Enable ticket create/upsert for selected customers, management tiers or alert classes. Persist counters in structured fields. Keep write-back and automatic recovery conservative; require human review for ambiguous correlation.

Phase 3 · Correlation and recovery automation

Turn on parent/child roll-up, precedence, flood control and recovery timers by policy cohort. Add SolarWinds acknowledgment/muting only after loop, permission and reconciliation tests pass.

Phase 4 · Generalized product capability

Extract reusable connector contracts, policy primitives, observability and admin experiences into the RMM/shared-integration platform. Avoid leaving COEO with a one-off prompt bundle only Revii engineers can support.

Final product call

Commit conditionally—and name the gap accurately.

Rev.io can propose a credible solution using Revii, New Rev.io ticketing/assets and the eventing/integration foundations. Today’s evidence does not support claiming that New Rev.io already provides COEO-grade SolarWinds orchestration.

  1. Position the commitment as a product build: SolarWinds connector + durable orchestration service + topology/policy control plane + New Rev.io platform enablement.
  2. Make Phase 0 and shadow-mode acceptance contractual gates: especially topology accuracy, ticket yield, false suppression and burst behavior.
  3. Keep Revii in the right role: configuration assistance, explanations, exception triage and operator interaction; deterministic services own correctness-critical state and writes.
  4. Do not promise write-back yet: SolarWinds acknowledgment/muting and status-aware recovery remain subject to exact API/version validation and New Rev.io ticket-event coverage.
  5. Fund reusable platform work: idempotent ticket writes, structured orchestration state, event replay/audit and reliable Service Ops webhooks should become shared New Rev.io capabilities rather than COEO-only code.
